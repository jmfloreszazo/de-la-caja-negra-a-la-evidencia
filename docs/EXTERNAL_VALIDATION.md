## What the current environment can establish

One hosted runner can execute real SQL transactions, distinct processes and containers, logical packet drops, client admission diagnostics and independent persisted-state checks. It can preserve an inconclusive activation witness honestly. These are useful repeatable observations. Several containers on that runner share its kernel, scheduler, memory, storage and physical failure domain.

A single-runner fixture cannot demonstrate independent-host HA, a real branch WAN, storage-controller power-loss durability, customer CICS/IMS fencing or an IBM Z comparison. Capacity and natural activation behavior are not intrinsically impossible on GitHub Actions: this campaign has simply not established them. Actions can orchestrate a dedicated distributed environment or self-hosted runners. Re-running the same shared-host fixture until it becomes green is not a substitute for that environment.

## Implementation work before a distributed campaign

1. Keep the archived loopback probes and their source hashes intact. Add a new driver/profile rather than weakening their endpoint guards. `lab/e2_b05_dispatch/run.py` currently asserts an exact loopback DSN, and `Program.cs` validates its disposable endpoint. The SQL monitor also fixes the database name. Merely changing an environment variable cannot convert this probe into a distributed benchmark.
2. Replace single-host `podman exec` and container-inspect assumptions in the new fixture transport. `lab/e2_account_directed/run_probe.py` delegates to the existing long-partition harness and compares clocks/processes in one host domain. Remote control must use explicit test-host identities and capture exit state, stdout and stderr before removal. Record actual placement; do not silently pin placement when measuring default behavior.
3. Synchronize host wall clocks and record measured offset/uncertainty before and after each run. Keep monotonic intervals local to their host. Cross-host overlap is established only when the intersection remains positive after uncertainty bounds; otherwise classify it INCONCLUSIVE. Reconcile operation IDs with authoritative SQL regardless of witness outcome. SQL-clock throughput windows also require bounded clock uncertainty.
4. Instrument client scheduling/admission, queue depth, connection acquisition, database lock and commit waits, WAL/flush and storage latency, CPU, memory, GC and network on each host. Distinguish observed correlation from a demonstrated bottleneck. With client cap 128 and pool 32, queued connection acquisition must be measured before interpreting the larger cap.
5. Use an isolated test environment, explicit endpoint allowlist, fixture identity, schema ownership and bounded fault scope. Separate credentials and control traffic from the faulted data path. A deployment preflight must refuse an unknown fixture; the existing loopback safety guards are not removed.

## Preregistered measurement plan

The following is a proposed protocol, not an executed result or a production sizing recommendation.

- First fill the existing performance contract with approved workload, deadlines, allowed miss/ambiguity rate, financial invariants, recovery objectives and cost scope. Record exact versions, CPU/memory quotas, storage and network configuration, images and topology. Do not infer vCPU from MIPS.
- First reproduce the 320/s direct diagnostic externally. Then sweep offered load on both sides of an observed degradation region; define the rates and stop conditions before each campaign. Use fixed seeded uniform, 5%-hot, single-hot and crossed profiles with independent offered streams. Do not adapt the offered rate to hide queue growth.
- Use at least three fresh repetitions per configuration, varied preregistered order and equal resources. As an initial study design, separate a 5-minute warmup, 15-minute steady interval and bounded drain. Retain the warmup and drain; never crop away overload. Longer soak runs follow only after the environment and correctness are stable. These durations are proposals, not acceptance thresholds inferred from hosted CI.
- Prove the generator has spare CPU/network capacity and can sustain the offer contract against a controlled sink before assigning a backend limit. Record every scheduled, dispatched, rejected, timed-out, ambiguous, acknowledged and SQL-committed operation. Include missed/deadline-failed offers in the service outcome denominator; survivor ACK latency is not service p99.
- Hold durability, pool, timeouts, retries and ledger semantics fixed while varying one factor; run pool/admission sweeps as separately identified configurations. Any retry must reuse the operation ID and retain all attempts. A capacity knee requires repeated queue/tail/deadline degradation plus attributable resource evidence, not just a semaphore reaching its cap.
- Inject one declared fault at a time: silo process, host/network domain, then SQL failover. Keep normal-service baselines, fault duration and recovery observations distinct. Record any manual restart as assisted recovery. A negative activation witness is not automatically a software failure, and a positive envelope is not global activation exclusivity.
- Independently read balances, operations, paired postings, outbox and ambiguous-ID resolutions after drain and failover. Preserve all seven financial checks and deliberate corruption controls. Missing data, corrupted invariants or lost acknowledged durability fail the applicable claim; infrastructure limitations do not waive them.
